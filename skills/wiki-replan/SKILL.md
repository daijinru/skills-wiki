# Wiki 增强的智能重规划器

当执行步骤失败且简单重试无法解决时，本技能介入进行**局部重规划**：分析失败根因、检索 Wiki 已知方案、重写受影响的步骤/里程碑、将失败经验沉淀到 Wiki。

用户输入：$ARGUMENTS

---

## 核心原则

1. **最小改动** — 只重写必要的部分，已完成的步骤和里程碑不动
2. **根因优先** — 先搞清楚为什么失败，再决定怎么改
3. **知识驱动** — 从 Wiki 中寻找已知解决方案，避免盲目试错
4. **经验留痕** — 无论最终方案如何，失败经验必须写入 Wiki

---

## 触发场景

本技能在以下场景被调用：

| 场景 | 触发方式 | 重规划范围 |
|------|----------|-----------|
| 步骤失败且重试无效 | `/wiki-replan` 或 `/wiki-execute` 失败后建议 | 当前步骤 → 同里程碑剩余步骤 |
| 技术路线不通 | 用户主动调用 `/wiki-replan` | 当前里程碑 → 可能影响后续里程碑 |
| 需求变更 | 用户主动调用 `/wiki-replan --scope milestone` | 指定里程碑及其后续 |
| 全局重规划 | 用户主动调用 + 确认 | 所有未完成的里程碑 |

## 执行步骤

### Phase 1：加载路线图与定位问题

#### 1.1 加载路线图

```bash
ls -lt .claude/roadmaps/*.md 2>/dev/null
```

文件定位逻辑同 `wiki-execute`：指定路径 > 唯一文件 > 让用户选择。

读取路线图完整内容。

#### 1.2 定位问题步骤

```
如果 $ARGUMENTS 包含 --from S{M}.{N}：
  → 从指定步骤开始重规划

如果路线图中存在 [!] 标记的步骤：
  → 自动定位到第一个失败步骤

如果没有失败步骤（用户主动调用）：
  → 定位到当前未完成的步骤
```

#### 1.3 确定重规划范围

```
$ARGUMENTS 包含 --scope step：
  → 仅重写当前失败步骤（替换为新方案）

$ARGUMENTS 包含 --scope milestone：
  → 重写当前里程碑的所有未完成步骤

默认（无 --scope）：
  → 智能判断：
    如果失败原因是步骤本身 → scope = step
    如果失败原因影响后续步骤 → scope = milestone
    如果失败原因动摇了技术路线 → 提示用户确认是否扩大范围
```

### Phase 2：失败根因分析

**这是重规划的核心起点。**

#### 2.1 收集失败证据

从路线图中提取：
- 失败步骤的描述和验收标准
- 失败步骤的错误备注（`[!]` 后的完成备注）
- 此前成功步骤的产出（排除产出缺失的可能）

```bash
# 检查前序步骤的产出物是否完整
for file in <previous_step_outputs>; do
  test -f "$file" && echo "✅ $file" || echo "❌ $file 缺失"
done
```

#### 2.2 分类失败原因

将失败归类为以下之一：

| 类别 | 特征 | 重规划策略 |
|------|------|-----------|
| **实现错误** | 代码 bug、配置错误 | 修正当前步骤，不需重规划 |
| **方案不可行** | 技术限制、依赖冲突 | 替换当前步骤的技术方案 |
| **前序缺陷** | 前面步骤的产出有问题 | 回溯修复 + 重规划受影响步骤 |
| **需求变更** | 用户改了需求 | 重新拆解受影响的里程碑 |
| **外部障碍** | 环境、网络、权限等 | 添加前置步骤或调整验收标准 |

#### 2.3 输出分析报告

```
╔══════════════════════════════════════════════════╗
║           🔍 失败根因分析                          ║
╠══════════════════════════════════════════════════╣
║                                                  ║
║  失败步骤: S{M}.{N} — <描述>                      ║
║  失败类别: <方案不可行 / 前序缺陷 / ...>           ║
║                                                  ║
║  📋 证据:                                         ║
║    • <错误信息或现象>                               ║
║    • <环境信息>                                    ║
║                                                  ║
║  🎯 初步判断:                                     ║
║    <一两句话的根因分析>                             ║
║                                                  ║
║  📐 重规划范围: <step / milestone / 需确认>        ║
║                                                  ║
╚══════════════════════════════════════════════════╝
```

### Phase 3：Wiki 方案检索

在确定失败原因后，从 Wiki 中寻找解决方案。

#### 3.1 构造检索查询

根据失败原因，生成针对性的检索关键词：

- 失败现象的关键词（如 "CORS", "timeout", "type error"）
- 涉及技术的关键词（如 "JWT", "Redis", "WebSocket"）
- 失败类别的关键词（如 "dependency conflict", "migration"）

#### 3.2 多层检索

```bash
# 标题匹配
ls wiki/pages/ 2>/dev/null | grep -i "<keyword>"

# 标签匹配（特别关注 confidence: low 的踩坑记录）
grep -rl "tags:.*<keyword>" wiki/pages/ 2>/dev/null

# 全文搜索
grep -rl "<error_keyword>" wiki/pages/ 2>/dev/null

# 链接追踪
grep "<matched_page>" wiki/index.md 2>/dev/null
```

#### 3.3 按 type 提取可用方案

读取命中的 Wiki 页面，按 `type` 字段定向提取：

- `type: solution` → 读取 `## 方案` + `## 验证结果` + `## 局限性`（直接可用的修复方案）
- `type: pattern` → 读取 `## 实现方式` + `## 适用场景`（替代技术路线）
- `type: pitfall` → 读取 `## 规避方法`（需要避开的坑）
- `type: decision` → 读取 `## 最终决策` + `## 理由`（架构层面的参考）

#### 3.4 输出检索结果

```
┌─────────────────────────────────────────┐
│  📚 Wiki 方案检索结果                     │
├─────────────────────────────────────────┤
│                                         │
│  🟢 直接方案:                            │
│    📄 [[cors-preflight]]                │
│       type: solution | confidence: high │
│       方案: 在 API 网关层统一处理 CORS   │
│                                         │
│  🔵 替代路线:                            │
│    📄 [[api-proxy-pattern]]             │
│       type: pattern | confidence: medium│
│       实现方式: 用本地代理绕过 CORS      │
│                                         │
│  ⚠️ 已知陷阱:                           │
│    📄 [[jwt-issues]]                    │
│       type: pitfall | confidence: high  │
│       规避方法: 不要在前端处理 Token 刷新│
│                                         │
│  ❌ 无直接方案的领域:                     │
│    → WebSocket + JWT 的组合场景无记录    │
│                                         │
└─────────────────────────────────────────┘
```

### Phase 4：生成重规划方案

基于根因分析 + Wiki 检索结果，生成具体的重规划方案。

#### 4.1 方案优先级

```
1. Wiki 中有 confidence: high 的方案 → 优先采用
2. Wiki 中有 confidence: medium 的方案 → 参考采用，增加验证步骤
3. Wiki 中无方案但有相关经验 → 基于经验设计新方案
4. Wiki 中完全无相关知识 → 从头设计，标注为"实验性"
```

#### 4.2 生成新步骤

根据重规划范围（step / milestone），生成替代步骤：

**Step 级重规划**：

```markdown
## 重规划方案: S{M}.{N} 替换

### 原步骤（已废弃）
- [!] **S{M}.{N}**: <原描述>
  - 失败原因: <...>

### 新步骤
- [ ] **S{M}.{N}a**: <新方案步骤1描述>
  - 验收: <验收标准>
  - 产出: <产出物>
  - 💡 Wiki来源: [[<page-name>]]

- [ ] **S{M}.{N}b**: <新方案步骤2描述>（如需要拆分）
  - 验收: <验收标准>
  - 产出: <产出物>
```

**Milestone 级重规划**：

```markdown
## 重规划方案: M{N} 剩余步骤重写

### 保留步骤（已完成）
- [x] S{M}.1: <...>
- [x] S{M}.2: <...>

### 废弃步骤
- [!] S{M}.3: <...> — 方案不可行
- [ ] ~~S{M}.4: <...>~~ — 因 S{M}.3 废弃而连带废弃
- [ ] ~~S{M}.5: <...>~~ — 同上

### 新步骤
- [ ] S{M}.3a: <新方案>
- [ ] S{M}.3b: <新方案>
- [ ] S{M}.4: <重写后的步骤>（如果仍需要）
```

#### 4.3 影响评估

检查重规划是否影响后续里程碑：

```
如果新步骤改变了产出物接口/格式：
  → 检查后续里程碑是否依赖这些产出
  → 如果是 → 列出受影响的后续步骤，标注需要同步调整
  → 在报告中明确标注影响范围

如果新步骤引入了新依赖：
  → 检查是否需要在前面追加安装/配置步骤
```

#### 4.4 方案确认

展示重规划方案，等待用户确认：

```
╔══════════════════════════════════════════════════╗
║           📐 重规划方案                            ║
╠══════════════════════════════════════════════════╣
║                                                  ║
║  范围: <step S{M}.{N} / milestone M{N}>          ║
║  策略: <替换方案 / 追加前置步骤 / 绕道方案>        ║
║  来源: Wiki [[<page>]] / 新设计                   ║
║                                                  ║
║  变更摘要:                                        ║
║    - 废弃: <N> 个步骤                             ║
║    + 新增: <M> 个步骤                             ║
║    ~ 修改: <K> 个步骤                             ║
║                                                  ║
║  对后续的影响:                                     ║
║    <无影响 / 需同步调整 M{X} 的 S{X}.{Y}>         ║
║                                                  ║
║  ⚠️ 请确认是否执行此重规划方案                      ║
║     (输入 "yes" 确认 / "no" 取消 / 提出修改意见)   ║
╚══════════════════════════════════════════════════╝
```

### Phase 5：应用重规划

用户确认后，将方案写入路线图。

#### 5.1 更新路线图文档

1. 将失败步骤标记为 `[!]` 并追加废弃说明
2. 在废弃步骤后插入新步骤
3. 如果是 milestone 级重规划，更新里程碑的步骤数
4. 更新里程碑总览表
5. 更新 frontmatter（`last_updated`、`total_milestones` 如有变化）

#### 5.2 追加变更日志

```markdown
| <时间> | 重规划 | S{M}.{N} 失败，替换为 S{M}.{N}a/b，参考 Wiki [[<page>]] |
```

#### 5.3 追加重规划记录

在路线图中当前里程碑章节追加：

```markdown
### 重规划记录 — <时间>

**触发原因**: S{M}.{N} 失败 — <失败原因>
**失败类别**: <方案不可行 / 前序缺陷 / ...>
**解决策略**: <替换方案来自 Wiki [[<page>]] / 全新设计>
**变更范围**: 废弃 <N> 步，新增 <M> 步
**影响评估**: <对后续里程碑的影响>
```

### Phase 6：经验沉淀到 Wiki

**无论重规划方案如何，失败经验必须写入 Wiki。**

#### 6.1 创建/更新失败经验页面

```bash
mkdir -p wiki/pages
```

**如果是全新的失败场景**（Wiki 中无相关页面），写入 `type: pitfall`：


## 三级应对策略总览

本技能实现了分级的失败应对机制，与 wiki-execute 协同工作：

```
Level 1: 步骤执行失败
    → wiki-execute --retry（自动重试）
    → 如果重试成功 → 继续
    → 如果重试失败 → 进入 Level 2

Level 2: 重试失败，查询 Wiki
    → wiki-replan 检索 Wiki 已知方案
    → 如果找到方案 → 应用方案，局部重写步骤
    → 如果没找到 → 进入 Level 3

Level 3: Wiki 无方案，全新重规划
    → wiki-replan 根据根因分析设计新方案
    → 可能扩大到 milestone 级重规划
    → 失败经验写入 Wiki（供未来检索）
```

## 边界情况处理

### 连续多次重规划

```
如果同一步骤已重规划 2 次以上：
  → 警告用户可能存在更深层问题
  → 建议检查前序里程碑的产出质量
  → 或考虑需求层面的调整
```

### 重规划影响已完成步骤

```
如果新方案需要修改已完成步骤的产出：
  → 明确标注回退风险
  → 列出受影响的文件/配置
  → 要求用户确认后执行
```

### 路线图已接近完成

```
如果项目已完成 >80% 的步骤：
  → 倾向于最小改动策略
  → 避免大范围重写导致前功尽弃
```

### Wiki 反馈闭环

```
当重规划方案被后续 wiki-execute 验证成功时：
  → wiki-execute 会自动将 confidence: low 更新为 medium/high
  → 形成"失败 → 记录 → 验证 → 成熟知识"的闭环
```

```

    │
    ├── 读取 → .claude/roadmaps/<name>.md (路线图)
    ├── 读取 → wiki/pages/* (方案检索)
    ├── 写入 → .claude/roadmaps/<name>.md (重写步骤)
    ├── 写入 → wiki/pages/* (失败经验)
    ├── 写入 → wiki/logs/* (重规划日志)
    ├── 更新 → wiki/index.md (索引维护)

    ├── 上游 → /wiki-execute 步骤失败时触发
    ├── 下游 → /wiki-execute 执行新方案
    ├── 回环 → /wiki-planner 如需全局重规划
    └── 底层 → /wiki 知识CRUD
```
